# Driver signing and distribution

This document states honestly what is required to install the TextDeck virtual
HID driver on Windows, what this repository does and does not do about it, and
what remains blocked.

## The problem

Windows will not load a kernel-mode driver whose package is not signed in a way
Code Integrity accepts:

- With **Secure Boot enabled and test signing disabled** (the normal state of a
  retail machine), the driver package must be signed by a certificate chaining
  to a Microsoft-trusted root. For a new driver that means either an
  **EV code-signing certificate** plus **Microsoft attestation signing**, or
  full WHQL/HLK certification.
- With **test signing enabled**, a self-signed certificate that the machine
  trusts is sufficient. Enabling test signing requires administrative action
  and a reboot, and it weakens the machine's code-integrity posture.

## What this repository provides

The build produces a **valid but self-signed-capable** driver package:

```
windows/driver/TextDeckHidDriver/x64/Debug/TextDeckHidDriver/
    TextDeckHidDriver.sys
    TextDeckHidDriver.inf
    textdeckhiddriver.cat      (generated by Inf2Cat, unsigned)
```

Note the directory shape: the MSBuild project lives in
`windows/driver/TextDeckHidDriver/`, and its `$(OutDir)` package lands another
`TextDeckHidDriver` below that. The path is
`windows/driver/TextDeckHidDriver/x64/Debug/TextDeckHidDriver/` — **not**
`windows/driver/x64/Debug/...`. `install_driver.ps1` defaults to the correct
one; the commands below use `$pkg` so they cannot drift from it.

`build_driver.ps1` builds with `/p:SignMode=Off`. It never:

- enables test signing,
- disables Secure Boot or HVCI,
- imports a certificate into any store,
- installs the driver.

Those are deliberate operator actions, documented below.

## Development and testing (self-signed, test signing)

Use a **dedicated VM**. Do not do this on a machine you rely on.

1. **Create a test certificate** (once, on the VM):

   ```powershell
   $cert = New-SelfSignedCertificate `
       -Type CodeSigningCert `
       -Subject "CN=TextDeck Test Signing (DEV ONLY)" `
       -CertStoreLocation Cert:\CurrentUser\My `
       -KeyUsage DigitalSignature `
       -KeyLength 2048 `
       -NotAfter (Get-Date).AddYears(3)
   $cert.Thumbprint
   ```

2. **Sign the SYS, regenerate the CAT, then sign the CAT.** Order matters: the
   catalog hashes the files it covers, so signing the SYS afterwards would
   invalidate it.

   ```powershell
   # Locate signtool from the installed kit rather than pinning a version.
   $st  = (Get-ChildItem "C:\Program Files (x86)\Windows Kits\10\bin" -Recurse -Filter signtool.exe -ErrorAction SilentlyContinue |
           Where-Object { $_.FullName -match '\\x64\\' } | Sort-Object FullName | Select-Object -Last 1).FullName
   $tp  = "<thumbprint from step 1>"
   # Derive the package directory instead of typing it: this is the very path
   # that drifted out of date in an earlier revision of this document.
   $pkg = Join-Path $PWD "windows\driver\TextDeckHidDriver\x64\Debug\TextDeckHidDriver"
   if (-not (Test-Path (Join-Path $pkg "TextDeckHidDriver.sys"))) { throw "package not found: $pkg (run windows\driver-tools\build_driver.ps1 first)" }

   & $st sign /v /fd SHA256 /s My /sha1 $tp /tr http://timestamp.digicert.com /td SHA256 "$pkg\TextDeckHidDriver.sys"
   & inf2cat /os:10_x64 /uselocaltime "/driver:$PWD\$pkg\"
   & $st sign /v /fd SHA256 /s My /sha1 $tp /tr http://timestamp.digicert.com /td SHA256 "$pkg\textdeckhiddriver.cat"
   ```

3. **Verify before installing** (all four must exit 0):

   ```powershell
   & $st verify /pa /v "$pkg\TextDeckHidDriver.sys"
   & $st verify /pa /v "$pkg\textdeckhiddriver.cat"
   & $st verify /pa /v /c "$pkg\textdeckhiddriver.cat" "$pkg\TextDeckHidDriver.inf"
   & $st verify /pa /v /c "$pkg\textdeckhiddriver.cat" "$pkg\TextDeckHidDriver.sys"
   ```

4. **Enable test signing** (requires a reboot, weakens code integrity):

   ```powershell
   bcdedit /set testsigning on
   shutdown /r /t 0
   ```

5. **Trust the public certificate** — export only the `.cer` (never the PFX) and
   import it into `LocalMachine\Root` and `LocalMachine\TrustedPublisher`.

6. **Install** with `windows/driver-tools/install_driver.ps1`. The installer
   refuses to proceed unless the catalog signature validates and covers both the
   INF and the SYS. It does not bypass any check.

## Checking a package you already have

`windows/driver-tools/verify_driver_package.ps1` performs the four `signtool`
checks above plus the structural ones that a half-finished signing run quietly
breaks — a STALE catalogue still verifies as a signed blob even though the file
order was wrong, so "the CAT is signed" is not the question. It asks:

- are the SYS, INF and CAT all present;
- does the INF still declare the TextDeck hardware ID and name the `.sys`;
- is the catalogue **not older** than the files it is supposed to cover (a SYS
  re-signed after `inf2cat` would make the catalogue stale);
- does the SYS verify, the CAT verify, and the CAT actually **cover** the INF
  and the SYS (`/c`).

It is read-only: it never signs, installs, imports a certificate or touches BCD.

```powershell
powershell -File windows/driver-tools/verify_driver_package.ps1
```

Exit codes: `0` all checks passed, `1` at least one failed, `2` package not
found (nothing was verified — this does not mean "fine").

Run against the package built on this host, it correctly reports the truth:
**7 passed, 4 failed** — every structural check passes and all four signature
checks fail with `No signature found`, because the build uses
`/p:SignMode=Off`. That is the expected result for an unsigned development
package, and it is why the installer gate refuses it.

## Production signing — what is blocked

**This repository does not ship a production-signed driver, and cannot.**

Attestation signing requires an EV code-signing certificate tied to a verified
legal identity and a Microsoft Partner Center account. Neither is available to
this project at the time of writing. Consequently:

- The driver package produced here is **not** ready for ordinary installation on
  a Secure Boot machine.
- Do not present it as such. A self-signed package that only loads with test
  signing enabled is a **development artifact**.

To close this gap, a maintainer with an EV certificate must submit the package
for attestation signing and publish the returned signed package. Until that
happens, the honest status is: **source-complete, self-signable, not
production-distributable as a driver.**

## Virtual HID identity is test-only

The current virtual HID reports `VID_1209` / `PID_0001`. pid.codes reserves
`1209:0001` for private testing only; it is not a universally unique product
identity and must not be used for a device that is redistributed, sold, or
manufactured. This project uses VHF to expose a virtual HID device, but that does
not grant a production identity. Keep this identifier limited to controlled
development/testing. Before distributing a production driver or product, obtain
an appropriate identity and update the code and verification expectations.
See <https://pid.codes/1209/0001/>.

## HVCI / Memory Integrity

HVCI is compatible with test-signed drivers only while test signing is on.
Disabling HVCI to load an unsigned driver is **not** an acceptable workaround and
is not documented as one here.

## What users can do today

The Windows application ships three backends and only one of them needs a
driver:

| Backend | Needs driver? | Needs admin? | Text coverage |
|---|---|---|---|
| Windows virtual HID (this driver) | yes | yes | US-layout characters |
| SendInput Unicode | no | no | any Unicode |
| ESP32-S3 USB HID | no (separate hardware) | no | US-layout characters |

A user who cannot or will not install a kernel driver can use the ESP32 backend
or the SendInput backend. That is why the driver is one backend rather than a
hard requirement.
